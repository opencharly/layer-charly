# 2026.269.2324 — feat(charly): pin the exact charly package so the install layer busts

## Summary

Pin an EXACT released charly version in `distro.<d>. package:` so a rebuilt
upstream package invalidates exactly the install layer (its RUN text changes),
instead of being silently ignored by BuildKit's cache.

- arch/debian/ubuntu/alpine: `charly` → `charly=2026.268.1917`
- fedora: `charly` → `charly-2026.268.1917`
- `candy.version` bumped `2026.243.0100` → `2026.268.1917`.

## Merge order — SATISFIED (the blocker is resolved)

The teardown guard that makes the pin safe is **merged to `origin/main`**:
`{{pkgName .}}` in the four distro `uninstall_template`s, landed as
**opencharly/charly#690** (merge `57a66ec1`, 2026-09-26T19:41Z; the earlier #667
was auto-closed at the review threshold and superseded by #690, which carries
every fix). Without the guard a pinned teardown breaks on the strict managers
(`pacman -Rs charly=2026.268.1917` → "target not found"; `apk del …` likewise) —
measured, and now guarded.

Two further defects the pin exposed were also fixed and merged in
**opencharly/sdk#307** (tag `v0.2026269.2108`), then adopted by
**opencharly/charly#695** (merge `dde3a395`) together with the plugin-pin bumps,
and the distro-side pins in **opencharly/distro-cachyos#97** (merge 2026-09-26T22:33Z):

1. `deploykit.distroRepoProvidesPackage` matched the bare `packaging.name`
   against the package list with `slices.Contains`, so the pinned entry no longer
   matched and the localpkg-skip did not fire — emitting a redundant UNPINNED
   second install that defeated the pin. Now matches on the bare name via the one
   canonical strip (`buildkit.PkgName`).
2. `packagekit.ParsePackaging` could not parse a real candy `charly.yml`
   (top-level `version:` scalar), so `charly generate-packages` failed on the
   localpkg path.
