# 2026.281.2113 — fix(pin): advance the four unserved charly pins to the served 2026.279.2144

## Summary

Every box composing this candy failed at the install step because four of the five per-distro
`charly` pins named a version the corresponding package repo no longer serves. Measured, after a
green `charly box validate`:

```
$ pacman --config /tmp/reposetup-pacman/pacman.conf --dbpath /tmp/reposetup-pacman/db \
      --cachedir /tmp/reposetup-pacman/cache -Sp charly=2026.268.1917
error: target not found: charly=2026.268.1917
exit=1
```

That is the error from layer-charly#15, reproduced here with the real client against the published
db. This PR advances the four literals that are no longer served to `2026.279.2144` — the version
each of those repos serves now — and leaves the fifth exactly where it is, with the reason.

**The five packaging repos do not share one version.** Each publishes ONE rotating artifact set per
`workflow_dispatch` (charly-arch/fedora/debian/ubuntu/alpine `build.yml`), so "the version the
distro repos serve" is per-arm, and a literal is correct iff its OWN repo serves it. Measured
2026-10-08T21:05Z against each published index:

| arm | published index | served version | this PR |
|---|---|---|---|
| charly-debian | `dists/stable/main/binary-amd64/Packages` | 2026.279.2144 | bumped |
| charly-ubuntu | `dists/stable/main/binary-amd64/Packages` | 2026.279.2144 | bumped |
| charly-fedora | `amd64/repodata/*-primary.xml.zst` | 2026.279.2144 | bumped |
| charly-arch | `amd64/charly.db` | 2026.279.2144 | bumped |
| charly-alpine | `amd64/x86_64/APKINDEX.tar.gz` | **2026.268.1917** | **left as is** |

`charly-alpine` still serves exactly `2026.268.1917`, so that literal is already the served one:
moving it to `2026.279.2144` would break the apk install with the same `target not found`. The
pin-block comment is rewritten to record the measured per-repo serving and the rule it implies,
instead of asserting that all five literals move together.

**Position on the pin's shape** (the operator's question in #15). An exact per-distro pin is the
RIGHT shape and must stay: the pin exists to invalidate the install layer, and the file records the
RCA that proved it — without it the install line is version-independent, BuildKit can never bust it,
and a rebuilt package is silently ignored (the githubrunner image baked a stale charly forever and
its welded plugin-review lacked the reasoning-effort/max-tokens knobs, so every large review returned
an empty completion). What is wrong is not the pin but the repos' retention: publishing one
overwritten artifact set per dispatch gives every pin a hard expiry, and the expiry fires in
consumers, at build time, as `target not found`. Advancing the pin fixes today's outage; it does not
remove the class. The durable fix is the second option in #15 — retain published versions in
charly-arch/fedora/ubuntu/debian/alpine — and that is a release-pipeline decision in those repos,
not in this candy, so this PR does not attempt it.

Sibling finding, same measurement: **charly-alpine is behind its four siblings** (last publish
packaged 2026.268.1917 while the other four have been republished at 2026.279.2144; charly itself is
at `v2026.281.1905`). A republish of charly-alpine is what makes the five literals converge again.
Not triggered from here — publishing another repo's package repo is neither this issue's scope nor
mine to do unasked.

Files: `charly.yml` only — the four literals, the corrected pin-block comment, and a comment on the
alpine block saying why it is not bumped. No candy behaviour, no `packaging:` metadata, no `plan:`
step changes.
